# AGENTS.md

Canonical instructions for coding agents and contributors.

## Tooling

- Use Bun for routine JavaScript and TypeScript package management, scripts, tests, and one-off commands: `bun`, `bun run`, and `bunx`. The Projen root owns an exact `bun` dev dependency from `BUN_VERSION`; `bun run bun` selects that workspace-local binary, while direct shell `bun` still uses the caller's global installation. Generated install tasks enforce `MINIMUM_BUN_VERSION`.
- Use the configured corporate registries. Do not work around blocked public registries with direct downloads.
- Use the root Projen definition as the source of truth. Change `.projenrc.ts` or `projen/src/**`, then run `bunx projen`; do not hand-edit generated files.
- Run repository-wide AI-SLOP Detector review through `bun run slop:review`. The generated `.slopconfig.yaml` mirrors `.gitignore`; any direct `slop-detector` invocation must pass `--config .slopconfig.yaml` so ignored trees such as `.tmp` are not scanned.
- Before adding helpers, dependencies, generators, or Databricks integrations, inspect existing `@dbx-tools/*` packages and load `dbx-tools-reuse`.
- Treat installed library and framework functionality as externally owned. Inspect the exact installed API, documentation, types, exports, and source before adding a local implementation for the same concern. Configure public APIs directly; do not wrap, subclass, copy, patch, or keep parallel policy for functionality the owner already provides.
- For Projen, use native project fields and components directly. A dbx-tools component may own only behavior Projen does not provide, and unsupported behavior must remain separate from the native owner.
- Prefer typed fields, options, and variables over string-keyed maps. Use maps only when keys are genuinely dynamic or an external API requires them.
- Pass bare logical environment keys to `configUtils`; its default scope adds `DBX_TOOLS_` automatically. Use the `DBX_TOOLS_` prefix only on exact process-environment constants read or serialized without configUtils, and never use the ambiguous `DBX_` prefix. Keep standard external variables such as `DATABRICKS_*`, `PYTHON`, and `UV_*` unchanged.
- For Databricks CLI operations that access a workspace, ask the user to select a profile and pass `--profile <name>`.
- Never use emojis in source, generated output, logs, docs, commit messages, or user-facing text.

## Repository Boundary

- The repository is JavaScript/TypeScript and Python only. Do not create or restore
  repository-owned Rust, Cargo, UniFFI, native binding, native binary installer,
  or native release packages unless an explicit requirement makes them necessary.
  Third-party native dependencies are allowed when an owning framework capability
  requires them or the user explicitly selects them; declare install-script/build
  allowances and preserve a supported portable fallback when the runtime may not
  provide the native binary.
- The monorepo changes in lockstep. Remove obsolete APIs instead of adding compatibility aliases or deprecated shims; update every in-repo caller in the same change.
- Types, records, enums, interfaces, and module shapes have one owner. Import the owning type directly or fix its generator/export surface rather than creating mirrors.
- Generated bindings, barrels, PythonMonkey bundles, and docs are derived artifacts. Fix their owner and regenerate them.

## Product Shape

`dbx-tools` provides companion packages for Databricks Apps, AppKit backends, Mastra agents, Genie workflows, Model Serving, Lakebase, approval-gated communication, and AppKit-oriented React UI.

For UI-only demo iteration, run `bun run demo -- -d` (`--watch-disable`) so AppKit's Vite middleware HMR updates the client without restarting the AppKit server, its sidecars, or its authenticated tunnel. Open the AppKit listen URL (default `http://127.0.0.1:8000`), not a separate client port. `dev:watch` watches the default workspace-package directories unless `--watch-include` globs are set, then drops `--watch-exclude` matches; `--watch-disable` / `-d` skips watching and runs the command once.

Primary ownership:

- `packages/js/shared/core/src/options.ts` owns common Databricks environment metadata, normalized URL and TCP/listener schemas, and schema-level option parse/serialization. `packages/js/cli/args` (`@dbx-tools/cli-args`) owns Commander argument binding and argv serialization.
- `packages/js/node/auth` owns Node/Bun Databricks auth option schemas, default environment/config credential resolution, profile selection, credential lifecycle, and token/header production for CLI-backed U2M, PAT, M2M, App SP/OBO, and an inert Python-runtime auth hook. Call `createAuthClient()` without parallel environment parsing when the default auth sources should apply. It does not own workspace HTTP APIs or construct SDK clients; consuming capability packages own their transport, while the Python Node runtime may install the SDK-backed process capability consumed by the hook.
- `packages/js/shared/auth` owns browser-safe passwordless and Databricks auth values, secret-free profile summaries, profile selections, and auth client field schemas.
- `packages/js/node/model` owns model discovery, catalogue caching, classification, ranking, protocol selection, reasoning policy, serving URL construction, and committed metadata snapshots. Native web search follows documented models and later intra-family versions from `versionTuple`; GPT-OSS does not inherit. Gateway capability overrides remain the disable path.
- `packages/js/node/model-protocol` owns Vercel AI SDK ProviderV4 construction, AI SDK message decoding/encoding, and framework-neutral Databricks serving-wire repair. `packages/js/shared/model` remains the owner of browser-safe wire schemas and content helpers.
- `packages/js/shared/model-gateway` owns browser-safe gateway schemas and model discovery clients. `packages/js/node/appkit-model-gateway` owns OpenAI Responses, Chat Completions, Anthropic Messages, embeddings, Codex, and Databricks AI Gateway transport. It reuses model-owned discovery and policy plus model-protocol-owned AI SDK transforms, prefers direct streaming fast paths, and uses AI SDK providers only for cross-protocol translation. OpenAI `capabilities.web_search` and Codex `supports_search_tool` follow discovered `webSearch`.
- `packages/js/cli/service` owns product-agnostic current-user install, start, stop, restart, status, uninstall, schema-or-object command option serialization, package-local Bun compilation into `~/.dbx-tools/bin`, service-owned uv Python environments, and systray2 menu behavior for consuming CLIs.
- `@dbx-tools/cli-args` owns Commander argument generation from Zod object schemas, including defaults resolved through `node/core` configUtils (environment, `.env`, bundle, and app YAML). Fields with `helpDefault: false` defer that loader until parsing and must not resolve configuration while rendering help. Consuming commands own their schemas. The consolidated CLI keeps command implementations behind subpath exports and dynamic imports.
- `@dbx-tools/cli/model-gateway` owns foreground `dbx model-gateway` and `dbx-model-gateway` execution plus its tray-only service definition and Models URL menu item. There is no Python gateway or compatibility command.
- `packages/py/graphiti` owns the one-process FastAPI composition of Graphiti's existing REST routers and MCP server, the PostGraph driver pinned from Graphiti PR 1777, persistent embedded PostgreSQL, and external Lakebase connections. The Projen Python source-sync engine copies the upstream REST, MCP, and driver subsets into the read-only generated tree at pinned commits so PyPI metadata contains no direct Git dependencies; change sync configuration instead of generated files. PythonMonkey owns model routing, authentication, Lakebase parsing, discovery, and per-connection credentials. `@dbx-tools/appkit-graphiti` owns typed option serialization, Python process supervision, and the AppKit Graphiti plugin exposed from its package root.
- The AppKit Graphiti supervisor must disable automatic parent-signal forwarding for its managed Python child. AppKit plugin shutdown owns sidecar termination after FastAPI lifespan cleanup; forwarding the original SIGINT directly makes Uvicorn re-raise `KeyboardInterrupt` and log a spurious canceled-lifespan traceback.
- `packages/js/node/lakebase` owns Lakebase parsing, discovery, and credentials. `packages/js/cli/lakebase-proxy` owns its listener, URL, and service option schemas plus the loopback PostgreSQL proxy.
- `packages/js/node/tunnel` and `packages/js/node/auth-gate` own tunnel transport, gate, and storage schemas and resolution. `packages/js/cli/tunnel` composes their fields with wrapper-only options. The tunnel process supervisor aborts its restart loop through `exec.onParentTerminationSignal` so a process-group signal that already stopped portr or frpc is not treated as a crash. Do not add a second `process` signal listener; exec's trap uses listener count to decide whether to re-raise. AppKit lifecycle shutdown awaits the supervisor, and tunnel children use exec's default 8-second graceful plus 4-second forced process-tree termination.
- `packages/js/node/postgres` owns advisory locks and the Postgres topic bus. Do not recreate Python counterparts; Python integrations should consume Node-owned behavior through generated PythonMonkey bindings when needed.
- `packages/js/node/appkit*`, `packages/js/shared/*`, and `packages/js/ui/*` own AppKit integrations and browser-safe contracts/UI. `@dbx-tools/ui` owns the common foundation plus branding, auth, email, and search subpaths; Mastra and Teams remain separate UI packages. Before changing AppKit-facing APIs, inspect `bunx @databricks/appkit docs` and installed AppKit `.d.ts` files.
- Mastra process-memory skills, including dbx-tools mounts, AI Tools, and startup-copied remote sources, are native agent-level skills exposed through Mastra's standard `skill`, `skill_search`, and `skill_read` tools. Do not include their virtual mounts in `SkillSearchProcessor`. Only skill directories loaded from Databricks Workspace paths use search-processor discovery because remote directory listing can be slow; exclude names already supplied as standard skills.
- `packages/js/node/appkit-sandbox` owns the AppKit integration for Databricks Sandboxes; `packages/js/shared/databricks-sandbox` owns its browser-safe Databricks-specific contracts. `src/_ssh.ts` owns the live command plus generic-pool abstractions, `src/_ssh_openssh.ts` owns pooled native ControlMaster and SOCKS5 resources, and `src/_ssh_ssh2.ts` owns pooled ssh2 clients and the guarded exec patch. The command pool keeps one tested connection warm and grows to ten; a separate zero-minimum forwarding pool prevents long-lived HTTP or WebSocket streams from consuming the warm command connection. Every borrowed resource is exclusive and destroyed after its command or forwarded stream because the Russh gateway may permit only one operation per connection lifetime. A failed forwarding open retries once with a fresh resource, but pool acquisition and an established HTTP or WebSocket stream are never retried or replayed. Native OpenSSH ControlMasters run behind a parent-owned pipe watchdog, and all native OpenSSH children also register with the shared exec termination hook and Node exit fallback; ssh2 sockets remain process-owned. Route shutdown begins before sessions close so expected stream endings do not produce proxy failures. Route mutation is serialized and rechecks shutdown after locking and listener creation. OpenSSH `ServerAliveInterval` and ssh2 `keepaliveInterval` own gateway liveness; do not add route-level keepalive. Pool create, test, destroy, acquire, forwarding, and shutdown paths are asynchronous; close awaits startup and in-flight session creation. SSH key publication uses cross-process check-lock-check with random staged files. `SshCommand` is the live Promise-compatible command handle: awaiting it returns the numeric exit code, `stdout` and `stderr` are live async iterables, and `result` owns the completed serialized shape. Session and runtime execution factories must return it synchronously because async functions assimilate thenables; REST, plugin, agent-tool, and other serialization boundaries await `result`. `sshTransport=auto` prefers native OpenSSH and otherwise selects ssh2 without runtime fallback; explicit `openssh` and `ssh2` modes never probe or switch to the other transport. `ssh2Patch=auto` attempts the missing exec-reply workaround only in development and continues unpatched when unavailable; `true` requires the patch and `false` never patches. Resolve those fields through bare configUtils keys `SANDBOX_SSH_TRANSPORT` and `SANDBOX_SSH_SSH2_PATCH`. `packages/js/node/appkit-sandbox/skills` owns packaged Sandbox showcase project recipes mounted read-only at `/.dbx-tools/skills` through one shared in-memory filesystem. Built-in terminal, desktop, and stats controls are product capabilities, not skills. Demo recipes must reuse assigned machines and `add_ssh_project`. Put complete known mise configuration directly in each skill or a skill-local reference instead of reconstructing it across calls. `config` accepts an object, a JSON object string, or a TOML string; string input is checked as JSON first and otherwise parsed as TOML before remote setup. First-class `env` merges over `config.env` for generated payloads such as `HTML_CONTENT`; reserved `PROJECT_NAME`, `PROJECT_PATH`, and `PROJECT_PORT` may be repeated only with the injected values. Generated mise settings remain project-owned. First-class `install`, `start`, and `uninstall` scripts map to hidden runtime-owned mise tasks. The runtime runs marker-gated install after `mise install`, runs boot-scoped start after installation and whenever the machine starts, and runs uninstall only during project removal or reset. Other mise tasks are user-invoked. Project lifecycle work is serialized through the home-owned lock/log. A failed project install or start is exposed as project state and log data without failing machine startup; a machine remains `starting` until every project reaches `ready` or `error`. Declare built-in service requirements through the project's typed `serviceDependencies` option; the runtime owns and waits for them outside project mise configuration. Projects that do not serve HTTP, including desktop applications, must set `route: false`. Before running a project task, list the available non-hidden tasks and use only a task whose purpose and invocation point are defined by the applicable skill; hidden runtime lifecycle tasks are not user controls. With `execute_ssh_command`, pass `command: "sh"` and put the shell script in `args: ["-lc", "..."]`; never pass an executable and its arguments together as `command`. Prefer declared mise tasks over ad-hoc workload commands. Bind routed services to loopback, use the returned user-prefixed path, avoid external CDNs when a self-contained browser implementation is practical, and state WebSocket path-prefix limitations when applicable. Project directory removal and reset run the hidden runtime-owned uninstall task when it exists, log and ignore failure, then stop remaining processes from `*.pid` files and any process whose cwd is the project directory before deleting `~/projects/<path>`. Project terminals opened inside a project directory must start an interactive shell through mise for that project without enabling automatic directory activation.
- Built-in terminal, desktop, and stats services are hidden machine-owned mise projects with reserved paths. Their installation and lifecycle shell belongs in packaged `mise.toml` definitions, not TypeScript strings. Guard install/start with Lakebase advisory plus home-owned remote check-lock-check state. One bounded operation log records the active attempt and result; lock waiters attach to that log instead of starting parallel work, and SSE/async-iterator callers receive the same generic service snapshots through `starting`, `ready`, or `error`. Running machines are the source of truth: list polling reconnects after an app restart, reads persisted lock/status/log files, and exposes enabled built-ins plus their logs from `machine.services`. Saved project install logs follow the same home-owned `lifecycle.log` files and appear on `SshProject.log` for the browser; agent `list_ssh_machines` and `list_ssh_projects` omit log bodies. UI controls and listeners must iterate shared built-in service metadata rather than add service-specific lifecycle code. Only `serviceDependencies` declared on `add_ssh_project` wait for readiness. Service dependencies remain typed project options owned by the runtime and must not be injected into project mise tasks.
- Every built-in service mise definition must provide hidden `start`, `stop`, and `status` tasks. Remote lifecycle inspection runs `status` before accepting a persisted `ready` marker and downgrades dead processes to `stopped`, so machine restarts and crashed services never expose a stale route as ready.
- SSH commands, project setup, and built-in services must not inherit authentication injected into a Sandbox machine. The SSH transport clears Databricks environment variables, disables agent forwarding, and points the default Databricks config path at `/dev/null` before every remote command. Generic `execute_ssh_command.env` overlays must reject Databricks credentials. If a Sandbox workload needs Databricks access, use a dedicated app-mediated capability that obtains the current user's short-lived OBO authorization for that operation; never expose or restore the app service principal in the Sandbox.
- Each Sandbox has exactly one Lakebase owner per workspace and machine. Direct loopback navigation in non-production has no Databricks front door to inject user headers, so a localhost SSH route may infer that sole owner. Every non-loopback route remains fail-closed without an explicit authenticated identity, including WebSocket upgrades.
- The gateway SSH username remains the Sandbox ID, but every public command, project, terminal, and service lifecycle runs as the locked non-sudo `sandbox-user` with home `/home/sandbox-user`. Default `machineSoftware` prepends `~/.local/bin` on PATH, then installs mise, Homebrew, and pkgx; PATH remains a standalone step when others are omitted. The privileged account bootstrap installs Homebrew's apt prerequisites and a `sandbox-user`-owned `/home/linuxbrew/.linuxbrew` prefix so the official installer runs without sudo, and the `brew` step adds `brew shellenv` activation. Sandbox software installs prefer mise, then Homebrew, then pkgx, never sudo or apt. Only package-owned fixed bootstrap and desktop prerequisite scripts may use the private privileged execution capability. Never expose sudo through REST, agent tools, Mastra, project configuration, machine software configuration, or user environment overlays.
- Graphical Sandbox recipes must declare the built-in desktop dependency and launch applications from the first-class project `start` field or an explicitly invoked user task through its service-owned `~/.dbx-tools/runtime/desktop/run` wrapper. Never enumerate X sockets, infer or rewrite `DISPLAY`, edit project launchers to target a display, or start, stop, replace, or reconfigure the desktop stack from a recipe.
- `packages/py/node-runtime` owns the trace-driven Node compatibility layer, shared `runtime.js` used by PythonMonkey bundles, and Databricks Python SDK auth injection for notebook and Job runtimes. Projen generates only package-specific bundles and thin Python adapters that import this runtime; it must not own or publish shim sources. Only shim Node built-ins actually imported by a bundle.

## Code And Generation Rules

- Public module namespaces come from capability-specific filenames; do not add filename-to-namespace repair maps.
- Browser clients for AppKit plugins must consume the plugin's published `clientConfig()` through shared exported schemas and derive every endpoint from shared exported route constants/builders. Never hard-code a plugin base path or keep parallel client/server route strings in node or UI packages.
- Keep `@dbx-tools/shared-core` logging dependency-free.
- Python Node bundles contain no production Python callbacks. Compatibility belongs in build-time shims.
- Use Zod for every type that crosses, or could plausibly cross, a serialization boundary: HTTP/SSE request and response bodies, upstream REST payloads, tool inputs/outputs, client config published to browsers, serialized env/JSON options, and persisted records. Define `XSchema`, document the schema and each field with `.describe()` (not JSDoc inside the object literal), and export `type X = z.infer<typeof XSchema>` (or `z.input` / `z.output` when defaults or transforms differ). Never export `type X = typeof XSchema`, and never keep a parallel interface for a schema-owned shape.
- Keep plain TypeScript interfaces and type aliases for in-process shapes: behavioral contracts and classes (`FileSystem`, clients, loggers), callables and generics, host objects (`Headers`, `URL`, `AbortSignal`, `Uint8Array`, `Date`), React props, parser results, and local helper option bags. Do not add Zod, or a `zod` dependency, to a package just to type those. Document them with ordinary JSDoc.
- Apply this when adding or changing a shared type; convert an existing interface only when it is or becomes wire data. Do not migrate utility packages wholesale.
- Generated API docs and `docs:check-source` accept either source: JSDoc on standard types, or `.describe()` on Zod schemas and their inferred aliases.
- `packages/js/shared/model/src/contracts.ts` owns browser-safe model contracts. Define schemas there and in sibling modules such as `openai-chat.ts`; do not generate a second contract surface.
- `packages/js/shared/model-gateway` owns compositional Zod gateway and browser-client contracts.
- `bun run --filter '@dbx-tools/model' metadata` refreshes committed model metadata. Normal synthesis must not perform network-backed metadata refreshes.
- Documentation is generated from root/package READMEs by `docs/scripts/sync-readmes.mjs`, with API pages from `docs/scripts/generate-api-docs.mjs`. Install the generated site with `bun install`. Run TypeDoc and Astro with Node (`docs/scripts/docs-toolchain.mjs` `DOCS_NODE`); do not use npm.

## Documentation

- Keep the root `README.md` focused on Databricks developer value.
- Write package READMEs for users: outcomes, runnable workflows, configuration, and operational limits. Keep development policies and implementation-history explanations out of product guides.
- Generate CLI command and option references from the owning parser's help or documentation API, including subcommands and forwarded options. Render each command as markdown tables for arguments, options, and child commands that command owns. Do not treat parent flags as global or repeat them on subcommands that do not declare them. Exclude built-in help commands and flags; do not maintain parallel option tables or hand-edit generated README sections.
- Put detailed workspace/generator guidance in `projen/README.md`.
- Track active technical debt under `docs/enhancements/YYYY-MM-DD-*.md`; move completed or abandoned plans to `docs/archived/enhancements`.
- Do not mention predecessor repositories or migrations in public docs.
- When changing future-agent behavior, update this file first.

## Releases

- `bun run bump` increments `VERSION` locally and synchronizes generated package versions.
- Run `bun run release` from any branch; without flags it retains all default steps. It commits and pushes pending branch changes, safely fast-forwards `main` when needed, then calls `bump`, commits the synchronized changes, pushes `main`, creates an annotated `vX.Y.Z` tag, and pushes the tag. It fails instead of creating a merge commit when `main` cannot fast-forward. Use `--no-bump` only for an existing synchronized bump.
- `.github/workflows/release.yml` runs only for `v*` tag pushes and verifies the tagged commit exactly equals `origin/main` before publishing Node, Python, and docs.
- The release workflow installs dependencies and validates/builds all release artifacts in one job. Install validation prerequisites before running validation tasks. Registry jobs only download and publish those artifacts; they must not install workspace dependencies or rebuild packages. Keep per-package Python environments and publish dependency ordering.
- Release task flags may select publication targets, documentation, optional validation, local registry publication, local dependency installation, optional demo-app deploy, and optional skip of release notes. Preserve unflagged defaults. Store CI selections in the annotated release tag, not a mutable repository setting; version and immutable-source verification remain mandatory. When validation is enabled, the local release runs `eslint:fix` before branch preparation and bump, then runs the selected fail-closed validation tasks; CI rebuilds release artifacts rather than checking generated-source fingerprints. `--demo-deploy` is off by default, runs locally after tagging, and is not stored in the tag. After bump and configured validation, `docs/releases/vX.Y.Z.md` is written with `dbx genie exec` (`--sandbox read-only --ephemeral`); the standard prompt forbids running tests or other validation commands, and on failure the step writes a short git-log summary instead. Release notes from `v0.9.61` onward are retained and published in the final docs sidebar section. Pass `--release-notes-text` or `--release-notes-file` to write supplied notes without Genie, `--release-notes-instructions` for run-specific additions to the standard prompt, or `--no-release-notes` to skip. Notes are not stored in the tag.
- There is no release PR, GitHub Release, manual stage recovery, Cargo/native publication, or alternate release entrypoint.
- Preserve local application/deployment flows and local npm/Python publication helpers.

## Validation

- Start with focused tests for changed packages, then broaden to relevant workspace tests and builds.
- Never guess or invent documentation routes, filenames, or heading anchors. Link only to a generated target that exists, and run `bun run docs:link-check` after changing README or documentation links. It validates generated Markdown routes and heading fragments without building the Astro site; keep the built-HTML link check as the final release backstop.
- Run `bunx projen` twice and ensure the second synthesis produces no additional diff when changing generated configuration.
- Run `bun run version:check` after version or workspace changes.
- Do not fix unrelated failures; report them clearly.
