# Repository code-quality audit

Date: 2026-10-30

Status: Complete

Archived: October 30, 2026

## Executive summary

- No critical or high-severity defect remained after the review.
- Repeated delay and path-normalization helpers bypassed existing owners. The
  release watcher and process shutdown now use `shared-core` `sleep()`, and the
  workspace test runner imports Projen's `toPosix()`.
- Eight public TypeScript declarations had no source documentation. The public
  declarations now have JSDoc, and an internal-only Projen helper is no longer
  exported.
- ESLint found 22 Prettier errors and one import-order warning. The affected
  TypeScript and TSX files were formatted and the demo entry import order was
  corrected.
- AI-SLOP Detector's initial sweep reported seven dead-code and 21 duplicate
  findings inside the vendored PostGraph driver. The generated scanner config
  now excludes that upstream-maintained tree.
- The unused-dependency sweep is not actionable for this monorepo. It evaluates
  the root manifests against imports from the complete workspace and treats
  configuration-only dependencies as unused.
- A resolved MLflow feedback defect remained in the active bug index. It is now
  archived.
- CLI README generation still required an obsolete `./cli` package subpath
  after package exports were consolidated into generated root entrypoints. It
  now accepts the root export while retaining `./cli` support for consumers
  that expose it.
- Machine-local skill activation links were removed from the repository. Skills
  remain machine configuration, not source-controlled project dependencies.

## Architectural mental model

The repository is a Bun-first TypeScript and Python monorepo generated by one
Projen root. Browser-safe schemas live under `packages/js/shared`, server
capabilities live under `packages/js/node`, React components live under
`packages/js/ui`, and CLI composition lives under `packages/js/cli`. Projen owns
workspace discovery, generated barrels, package manifests, TypeScript
configuration, Python source synchronization, bindings, validation tasks, and
release orchestration.

Databricks AppKit and Mastra own application and agent framework behavior.
dbx-tools adds Databricks-specific policy, protocol adaptation, lifecycle
coordination, and shared contracts where those frameworks do not expose an
equivalent public capability. The Graphiti package includes synchronized
upstream sources and a PostGraph-derived driver; those files must be changed
through their sync or upstream owner rather than local cleanup edits.

## Top five priorities

1. Keep utility ownership checks active. New sleep, path, error, JSON, and
   concurrency helpers should use `@dbx-tools/shared-core` or the narrower
   package owner.
2. Keep the source-documentation ratchet green. Public declarations exposed by
   generated barrels need direct JSDoc or schema descriptions.
3. Keep structural scans focused on handwritten code. Synchronized upstream and
   generated trees should be excluded through `.projenrc.ts`.
4. Keep formatting in the repository validation path. Run `eslint:fix` before a
   release so routine formatting debt does not accumulate.
5. Split large generator files only with an ownership boundary and output-parity
   tests. Line count alone is not a reason to add another abstraction.

## Things that look bad but are actually fine

- The PostGraph operation modules contain repeated record conversion and delete
  functions. They are an attributed upstream-derived driver with separate
  operation classes, not handwritten dbx-tools utility duplication.
- `runtime.py` uses process globals. PythonMonkey runtime and JavaScript module
  singleton identity require a process-wide registry.
- `project-js.ts` and `python-node-bindings.ts` are large. Both are cohesive
  generator owners with extensive synthesis and output tests; splitting by line
  count would add coordination without removing policy.
- The root manifest has dependencies that do not appear in ordinary source
  imports. ESLint plugins, type packages, Projen, and release tooling are loaded
  through configuration and generated tasks.
- Generated PythonMonkey bundles show large diffs after source or generator
  changes. They are derived artifacts and must be reviewed against their owner,
  not edited directly.

## Open questions

- Whether the PostGraph driver should move back under an explicit generated
  directory is an ownership decision for the Python sync design, not a cleanup
  edit.
- Future work may split the JavaScript Projen project or Python binding
  generator when a concrete feature provides a stable extraction boundary.

## Validation

- `bun run shared-core:usage` reported 129 runtime exports with no unused
  exports.
- The initial AI-SLOP Detector review passed with `should_fail_build: false` and
  no boundary or stale-suppression findings.
- Projen synthesis completed twice after the owner changes.
- `bun run eslint` and `bun run compile` passed; compilation checked 43
  workspaces.
- `bun run test` passed the 310 selected JavaScript and TypeScript test files
  plus both 64-test Python runs. The generated upstream Graphiti code emitted
  six Pydantic deprecation warnings.
- `docs:check-source`, `docs:check-readmes`, and `docs:link-check` passed. The
  source documentation baseline now contains no undocumented public TypeScript
  symbols.
- `version:check`, the registry-neutral Bun lockfile check, `git diff --check`,
  and `shared-core:usage` passed.
- The final AI-SLOP Detector review passed with `should_fail_build: false`; the
  vendored PostGraph findings were absent.
- `bun audit --json` could not query advisories because the configured registry
  returned `404` for the npm advisory bulk endpoint. No public-registry bypass
  was attempted.
