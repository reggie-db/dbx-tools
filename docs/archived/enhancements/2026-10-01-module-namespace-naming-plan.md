# Module Namespace Naming Cleanup

**Status:** Completed on `dev`.

## Goal

Remove recurring repository-owned import aliases such as
`async as asyncTools`, `config as coreConfig`, `project as projectApi`, and
`plugin as emailPlugin`. Public namespaces should describe the capability they
own, and the source filename should be the single source of truth for the name
generated by the Projen barrel.

## Naming policy

- A compound source filename generates its camel-cased namespace directly:
  `config-utils.ts` becomes `configUtils`. Hyphens and underscores follow the
  same rule.
- There is no filename-to-namespace map or compatibility alias table.
- Feature factories are imported directly from their package root when their
  names already describe the consumer action, such as `email`, `search`,
  `teams`, `mastra`, `webSearch`, and `graphiti`.
- An alias remains only when two independent owners expose the same symbol or
  when an internal generated-binding bridge benefits from an implementation
  distinction. Those aliases identify their source.
- Generated barrels and declarations are regenerated from their owning source.

## Feature entry points

Package-root exports now make the commonly aliased feature functions available
directly. Email exports `email`, `emailTool`, `defaultEmailBrand`, and
`emailBrandFromContext`. Tunnel exports `authGate` and `tunnelInterceptor`.
Other feature packages already exposed their factories directly, so consumers
were changed to use those exports instead of aliases of generic `plugin` or
`tool` namespaces.

The Projen package uses `project` as its filename-derived namespace, and
constructed repository roots are named `rootProject`. This removes the repeated
`project as projenProject` import without changing the conventional
`DBXToolsRustProject`, `DBXToolsNodeProject`, and `DBXToolsPythonWorkspace`
class names.

## Regression coverage

- Barrel tests cover both `config-tools.ts` and `config_tools.ts` generating
  `configTools` without configuration.
- The packed external-consumer test installs local archives of the engine and
  all affected internal dependencies, synthesizes twice, and compiles and tests
  generated Node and Rust projects. Per-package file overrides keep that test
  isolated from older published package surfaces.
- Repository synthesis, compilation, linting, package tests, language tests,
  docs checks, and formatting checks provide the release validation.

## Intentionally retained aliases

Source-qualified aliases remain for genuine collisions such as AppKit versus
Databricks `WorkspaceClient` types and shared versus AppKit search request
types. Internal generated-binding adapters retain `Native`, `Rs`, or `withRust`
names where the implementation distinction is useful. Established `-rs`
package names remain unchanged.

No deprecated namespace compatibility exports or replacement `-native`
packages were added.
