# Release 0.9.9

Reviewing the changed files to produce an accurate release summary from the diff.
Version 0.9.9 tightens the per-user `dbx model-proxy service` install path so background services launch a stable copy under your config directory, and it adds a machine-readable install preflight that release wrappers can call before registration. Documentation and contributor guidance were updated to match.

### Model proxy service

- Service install copies the headless proxy and optional desktop companion into `<config-dir>/bin` before registration, so launchd, systemd, or Windows login startup no longer point at a Cargo build output or a versioned CLI download cache file.
- The hidden `service requirements` command emits JSON describing resolved install arguments, systray policy, and whether the desktop companion asset is required or supported, for `@dbx-tools/rust-binary` and other orchestrators that forward lifecycle flags without duplicating validation.
- Normal service commands still print JSON status to stdout; requirements mode is used only for preflight.
- Install rejects user-supplied `--config-dir`, `--persistence`, and `--service-mode` in the server argument tail; those options belong before the `--` separator because the lifecycle injects them for the installed process.
- When the desktop companion is requested but missing from the build, the proxy logs a clear warning instead of failing silently.

### `dbx-tools-service`

- Shared lifecycle crate gains managed executable staging (atomic copy into `bin/`, cleanup on uninstall, Windows-friendly replace) and the requirements resolver that reuses the same install argument parsing as `service install`.
- Companion capability probing and `auto`, `always`, and `never` systray policy integrate with the requirements output so release installs can decide whether to bundle the desktop binary.
- README documents the managed executable copy, requirements preflight, and Windows supervision behavior.

### Contributor and release tooling

- `AGENTS.md` documents that service install must register the stable config-dir binary and that JavaScript release wrappers consume the requirements argv without reimplementing lifecycle rules.
- Projen release and local UniFFI publish tests were extended to cover the updated release flow.
